# Claude Code skills / plugins / MCP ecosystem: mechanics, installation, effective and safe use (state as of Oct 2026)

Version context: the latest Claude Code release in the official changelog when these notes were written is v2.1.303 (October 18, 2026) — [Changelog](https://code.claude.com/docs/en/changelog). Many features below have version gates (v2.1.2xx). If a command does not work, run `claude update` / check `claude --version` first.

Method note: official Claude Code docs pages were downloaded as raw Markdown (`https://code.claude.com/docs/en/<page>.md`) and read in full where relevant, so the quotes and commands below come straight from the current docs rather than from search snippets. agentskills.io, snyk.io, skillsmp.com, claude-plugins.dev, cursor.com and developers.openai.com could not be reached directly from the research environment (proxy/DNS blocks). For those, facts come from the GitHub source of the same content (Agent Skills spec), from search-engine summaries, or are listed under Gaps.

## 1. What Agent Skills are, where they live, how Claude loads them, and how they differ from MCP, slash commands, subagents and hooks

### Takeaway
A skill is a folder holding a `SKILL.md` file (YAML frontmatter plus Markdown instructions), with optional bundled scripts, references and assets. Only each skill's name and description sit in context all the time. The body loads when you type `/skill-name` or when Claude matches the description to the task, and bundled files load only when Claude reads or runs them. Use skills for knowledge and procedures, MCP for live external tools and data, subagents to keep heavy work in a separate context, hooks for rules that must run every time, and plugins to package and distribute all of these. Custom slash commands have been merged into skills.

### Cited Findings
**Format and standard**
- Claude Code skills follow the [Agent Skills](https://agentskills.io) open standard, "which works across multiple AI tools". Claude Code adds its own features on top, such as invocation control, subagent execution and dynamic context injection — [Claude Code: Skills](https://code.claude.com/docs/en/skills)
- Anthropic introduced Agent Skills on Oct 16, 2025, then published them as an open standard "for cross-platform portability" on December 18, 2025 — [Anthropic Engineering: Equipping agents for the real world with Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)
- Spec directory layout: `skill-name/SKILL.md` (required), plus optional `scripts/` (executable code), `references/` (docs, e.g. `REFERENCE.md`) and `assets/` (templates, images, data) — [Agent Skills specification (source: agentskills/agentskills repo)](https://github.com/agentskills/agentskills/blob/main/docs/specification.mdx)
- Spec frontmatter: `name` is required: 1–64 chars, lowercase `a-z`, `0-9` and `-` only, no leading, trailing or consecutive hyphens, and it "Must match the parent directory name". `description` is required: 1–1024 chars, saying what the skill does and when to use it. Optional fields are `license`, `compatibility` (≤500 chars), `metadata` (a string→string map) and `allowed-tools` (space-separated, marked "Experimental"). Validate with `skills-ref validate ./my-skill` — [Agent Skills specification](https://github.com/agentskills/agentskills/blob/main/docs/specification.mdx)
- Anthropic platform rules for `name`: max 64 chars, lowercase letters, numbers and hyphens, no XML tags, and must not contain the reserved words "anthropic" or "claude". `description`: non-empty, max 1024 chars, no XML tags — [Claude Platform: Agent Skills overview](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview)
- **Conflict / difference:** in Claude Code, "All fields are optional. Only `description` is recommended". `name` defaults to the directory name, and an omitted `description` falls back to the first non-empty line of the body. However, claude.ai uploads, the Skills API and `package_skill.py` from anthropics/skills accept only `name`, `description`, `license`, `compatibility`, `metadata` and `allowed-tools`. They fail with a hard error on any other key, e.g. `Unexpected key(s) in SKILL.md frontmatter: argument-hint` — [Claude Code: Skills](https://code.claude.com/docs/en/skills)
- Claude Code-only frontmatter fields: `when_to_use`, `argument-hint`, `arguments`, `disable-model-invocation`, `user-invocable`, `disallowed-tools`, `model`, `effort` (`low|medium|high|xhigh|max`), `context: fork`, `agent`, `background`, `hooks`, `paths` (globs), `shell` (`bash`/`powershell`). An unrecognized field is ignored silently — [Claude Code: Skills](https://code.claude.com/docs/en/skills)

**Progressive disclosure (how loading works)**
- Level 1, metadata (`name` and `description`): always loaded at startup, about 100 tokens per skill. Level 2, the SKILL.md body: loaded when triggered, under 5k tokens. Level 3+, resources: "None until accessed". Scripts run through bash "and only their output enters context" — [Claude Platform: Agent Skills overview](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview)
- In Claude Code, by default the "Description [is] always in context, full skill loads when invoked". With `disable-model-invocation: true` the description is not in context at all, and only the user can invoke the skill. With `user-invocable: false` only Claude can invoke it and it is hidden from the `/` menu — [Claude Code: Skills](https://code.claude.com/docs/en/skills)
- The skill listing budget "scales at 1% of the model's context window". When it overflows, Claude Code drops descriptions, starting with the least-invoked skills, while every skill name stays listed. Each entry's `description` + `when_to_use` text is capped at 1,536 chars. You can tune this with `skillListingBudgetFraction` (e.g. `0.02`), `SLASH_COMMAND_TOOL_CHAR_BUDGET` or `skillListingMaxDescChars` — [Claude Code: Skills](https://code.claude.com/docs/en/skills)
- Once invoked, the rendered SKILL.md "enters the conversation as a single message and stays there across later turns". Claude Code doesn't re-read the file on later turns. After auto-compaction it re-attaches the first 5,000 tokens of each invoked skill, within a combined 25,000-token budget — [Claude Code: Skills](https://code.claude.com/docs/en/skills)
- Dynamic context injection: a line like `` !`git diff HEAD` `` in SKILL.md runs before Claude sees the content and is replaced by the command's output (a Claude Code-only feature) — [Claude Code: Skills](https://code.claude.com/docs/en/skills)
- Arguments: `$ARGUMENTS` (and named `$name` via the `arguments` field) are replaced with whatever follows `/skill-name` — [Claude Code: Skills](https://code.claude.com/docs/en/skills)

**Where skills live (Claude Code)**
- Enterprise: `.claude/skills/<skill-name>/SKILL.md` in the managed settings directory. Personal: `~/.claude/skills/<skill-name>/SKILL.md`, which loads in all your projects but "not Cowork or cloud sessions". Project: `.claude/skills/<skill-name>/SKILL.md` (commit it to share with the team). Nested: `<subdir>/.claude/skills/...`. Additional directories added via `--add-dir`. Plugin: `<plugin>/skills/<skill-name>/SKILL.md`, invoked as `/plugin-name:skill-name`. Skills synced from your claude.ai account go to `~/.claude/skills/synced/` and are invoked as `/anthropic-skills:<name>` — [Claude Code: Skills](https://code.claude.com/docs/en/skills)
- Name precedence: enterprise beats personal, and personal beats project. A user skill replaces a bundled skill or built-in command of the same name, but not its aliases. Plugin skills never collide because they are namespaced — [Claude Code: Skills](https://code.claude.com/docs/en/skills)
- Project skills load from `.claude/skills/` in the start directory and every parent directory up to the repo root. Skills in subdirectories below the start directory load the first time Claude touches a file there — [Claude Code: Skills](https://code.claude.com/docs/en/skills)
- Don't name a folder `synced` or `anthropic-skills` (both reserved). Folders may be symlinks. A skill folder that contains `.claude-plugin/plugin.json` loads as a plugin named `<name>@skills-dir` — [Claude Code: Skills](https://code.claude.com/docs/en/skills)
- Cloud sessions (claude.ai/code) and routines don't read `~/.claude/skills/`. They load skills enabled on your claude.ai account and project skills committed to the repo — [Claude Code: Skills](https://code.claude.com/docs/en/skills)
- **Renamed or merged feature:** "Custom commands have been merged into skills." `.claude/commands/deploy.md` and `.claude/skills/deploy/SKILL.md` both create `/deploy`. The old format still works, but skills add supporting files and auto-invocation. If both exist with the same name, the skill wins. The old URL `code.claude.com/docs/en/slash-commands` now serves the skills page — [Claude Code: Skills](https://code.claude.com/docs/en/skills)
- Bundled skills include `/doctor`, `/code-review`, `/batch`, `/debug`, `/loop`, `/claude-api`, `/run`, `/verify` and `/run-skill-generator`. You can disable them with `disableBundledSkills` — [Claude Code: Skills](https://code.claude.com/docs/en/skills)

**Skills vs other extension types (official comparison)**
- CLAUDE.md is persistent context loaded every session, for "always do X" rules. A skill holds "Reusable content, reference docs, repeatable tasks". A subagent is an "Isolated execution context that returns summarized results". MCP will "Connect to external services". A hook is a "Script, HTTP request, MCP tool call, prompt, or subagent triggered by events". Plugins are "the packaging layer" that bundles skills, hooks, subagents and MCP servers into one installable unit — [Claude Code: Extend Claude Code](https://code.claude.com/docs/en/features-overview)
- MCP vs skill: "MCP connects Claude to external services. Skills extend what Claude knows, including how to use those services effectively", and the two are designed to work together — [Claude Code: Extend Claude Code](https://code.claude.com/docs/en/features-overview)
- Hook vs skill: a hook "Fires on its event without Claude deciding" and costs zero context unless it returns output. With a skill, "Claude interprets the instructions; outcome can vary". "If a rule must hold every time, make it a hook rather than a prompt instruction" — [Claude Code: Extend Claude Code](https://code.claude.com/docs/en/features-overview)
- Skill vs subagent: a skill adds to the main context window, while a subagent "Uses a separate window" and returns only a summary. They combine through the subagent `skills:` field (which preloads full skill content) or the skill `context: fork` field — [Claude Code: Extend Claude Code](https://code.claude.com/docs/en/features-overview)
- Subagents are Markdown files in `~/.claude/agents/` (personal) or `.claude/agents/` (project) — [Claude Code: Subagents](https://code.claude.com/docs/en/sub-agents)
- `context: fork` does NOT fork the conversation. The forked subagent "doesn't see your conversation history", runs in the background by default (`background: false` makes it wait), and "only makes sense for skills with explicit instructions" — [Claude Code: Skills](https://code.claude.com/docs/en/skills)
- Suggested order for adding extensions: a repeated mistake goes in CLAUDE.md; a repeated prompt becomes a user-invocable skill; a playbook pasted for the third time becomes a skill; data you keep copying from a browser tab means an MCP server; a side task that floods context goes to a subagent; "something to happen every time" is a hook; a second repo needing the same setup means a plugin — [Claude Code: Extend Claude Code](https://code.claude.com/docs/en/features-overview)

### Inferences
- For the downstream recommendations (frontend, SVG, video, 3D): a "skill" is the right container for style guides, library conventions (e.g. Three.js, Remotion, SVG optimization rules) and render/verify scripts. An "MCP server" is the right container for live tools such as a browser, Figma or a renderer API. Many vendors ship both together as one plugin.
- When a recommended skill must also work in claude.ai or through the API, keep its frontmatter to the six spec fields. Otherwise upload fails.
- The spec says `name` must match the directory name, while Claude Code tolerates a mismatch. Keeping them identical avoids cross-agent breakage.

### Gaps
- agentskills.io itself (client showcase, list of adopting products) could not be fetched. The spec text came from its GitHub source. The full list of clients adopting the standard is not verified here.

## 2. How Claude Code plugins and plugin marketplaces work (commands, official marketplaces, marketplace.json, scopes, team sharing)

### Takeaway
A marketplace is a git repo (or a local path or URL) with `.claude-plugin/marketplace.json`. You register it once with `/plugin marketplace add <owner>/<repo>`, then install with `/plugin install <plugin>@<marketplace-name>`. You choose user, project or local scope, and the choice is written to `enabledPlugins` in the matching settings file. The official marketplace `claude-plugins-official` (repo `anthropics/claude-plugins-official`) is added automatically. `anthropics/claude-code` is only a demo marketplace, and `anthropics/skills` is a separate topic marketplace named `anthropic-agent-skills`.

### Cited Findings
**Anthropic's marketplaces**
- Anthropic runs three general marketplaces. Official: repo `anthropics/claude-plugins-official`, marketplace name `claude-plugins-official`, "added the first time you start an interactive terminal session". Community: repo `anthropics/claude-plugins-community`, marketplace name `claude-community` (not the repo name), added with `/plugin marketplace add anthropics/claude-plugins-community`. Demo: repo `anthropics/claude-code`, marketplace name `claude-code-plugins` — [Claude Code: Anthropic's marketplaces](https://code.claude.com/docs/en/plugins/anthropic-marketplaces)
- **Outdated-instructions flag:** "If a tutorial or an older set of instructions tells you to run `/plugin marketplace add anthropics/claude-code`, that adds the demo marketplace ... It isn't the official marketplace." Install shared plugins such as `code-review`, `feature-dev`, `commit-commands` and `security-guidance` from `claude-plugins-official` "so you don't have two copies installed" — [Claude Code: Anthropic's marketplaces](https://code.claude.com/docs/en/plugins/anthropic-marketplaces)
- Anthropic also publishes topic marketplaces such as `anthropics/skills` and `anthropics/knowledge-work-plugins`, added with `/plugin marketplace add <owner>/<repo>` — [Claude Code: Anthropic's marketplaces](https://code.claude.com/docs/en/plugins/anthropic-marketplaces)
- anthropics/skills: `/plugin marketplace add anthropics/skills`, then `/plugin install document-skills@anthropic-agent-skills` or `/plugin install example-skills@anthropic-agent-skills`. The docx/pdf/pptx/xlsx skills are "source-available, not open source", the rest are mostly Apache 2.0, and the repo is "for demonstration and educational purposes only" — [anthropics/skills README](https://github.com/anthropics/skills)
- The anthropics/skills `marketplace.json` has name `anthropic-agent-skills` and lists `document-skills`, `example-skills`, `claude-api`, `academy-guide` and `discernment-nudge` (at fetch time) — [anthropics/skills marketplace.json](https://github.com/anthropics/skills/blob/main/.claude-plugin/marketplace.json)
- The official marketplace's `marketplace.json` had 315 plugin entries at fetch time. `/plugins` holds Anthropic-maintained plugins and `/external_plugins` holds third-party ones from partners. Install with `/plugin install {plugin-name}@claude-plugins-official` — [anthropics/claude-plugins-official](https://github.com/anthropics/claude-plugins-official)
- Official-marketplace entries relevant to frontend, visual and media work (at fetch time): `frontend-design`, `playwright` (Microsoft's browser-automation MCP), `chrome-devtools-mcp`, `figma`, `canva`, `adobe-for-creativity`, `superdesign`, `playground` (interactive HTML playgrounds), `hyperframes` (HeyGen: "Write HTML, render video ... GSAP"), `runway-api` (video generation), `modern-web-guidance` (GoogleChrome), `vercel`, `context7` (up-to-date docs MCP), `skill-creator`, `plugin-dev`, `mcp-server-dev`, `security-guidance` and `claude-security`. No Remotion, Blender or Three.js entry turned up on a keyword search of the catalog — [claude-plugins-official marketplace.json](https://github.com/anthropics/claude-plugins-official/blob/main/.claude-plugin/marketplace.json)
- You can browse the catalog on the web at [Claude Marketplace](https://claude.com/marketplace/plugins), which shows install counts and an "Anthropic verified" mark, or in the **Discover** tab of `/plugin` — [Claude Code: Anthropic's marketplaces](https://code.claude.com/docs/en/plugins/anthropic-marketplaces)

**Install flow and scopes**
- In a session, `/plugin install commit-commands@claude-plugins-official` opens a details pane instead of installing right away. The pane shows **Will install** (commands, agents, skills, hooks, MCP/LSP servers) and, for official-marketplace plugins, a **Context cost** with "Every turn" and "When invoked" token estimates. You then pick a scope: user, project or local — [Claude Code: Install and manage plugins](https://code.claude.com/docs/en/plugins/install)
- User scope is written to `enabledPlugins` in `~/.claude/settings.json`, project scope to `.claude/settings.json` (committed), and local scope to `.claude/settings.local.json`. When scopes disagree, local overrides project and project overrides user — [Claude Code: Install and manage plugins](https://code.claude.com/docs/en/plugins/install)
- Team caveat: committing a project-scope entry "turns the plugin on for your collaborators but doesn't download it to their machines". Each collaborator runs `claude plugin install <name>@<marketplace> --scope project` once — [Claude Code: Install and manage plugins](https://code.claude.com/docs/en/plugins/install)
- Shell (non-session) commands: `claude plugin install <p>@<m> [--scope project|local]` (default scope is user), `claude plugin enable|disable|uninstall <p>@<m>`, `claude plugin list`, `claude plugin details <name>` (prints an `Always-on` token cost), `claude plugin update <p>@<m>`, `claude plugin marketplace add|list|update|remove`, `claude plugin validate <dir>` and `claude plugin prune`. On a fresh machine, scripts must run `claude plugin marketplace add anthropics/claude-plugins-official` before installing from it — [Claude Code: Install and manage plugins](https://code.claude.com/docs/en/plugins/install)
- Add and install in one step: `/plugin install deploy-helper --marketplace your-org/plugins` (in-session, v2.1.275+) or `claude plugin install deploy-helper --marketplace your-org/plugins` (shell, v2.1.292+) — [Claude Code: Install and manage plugins](https://code.claude.com/docs/en/plugins/install)
- Marketplace sources: `owner/repo`, optionally `#ref` to pin a branch or tag (e.g. `your-org/plugins#v1.2.0`); a full git URL (`https://...git#v1.0.0`); a local path, which must start with `./` or `../` because a bare `name/name` is read as GitHub; or an `https://.../marketplace.json` URL. `/plugin market` is a short form — [Claude Code: Install and manage plugins](https://code.claude.com/docs/en/plugins/install)
- Changes made in the `/plugin` panel are applied through `/reload-plugins` (`--force` if it would invalidate the prompt cache). Plugin skills show up as `/<plugin>:<skill>` — [Claude Code: Install and manage plugins](https://code.claude.com/docs/en/plugins/install)
- Auto-update is on by default for `claude-plugins-official` and the other official names (except `knowledge-work-plugins` and `first-party-plugins`). It is off by default for the community marketplace, third-party marketplaces and local ones. Toggle it per marketplace under `/plugin` → **Marketplaces** — [Claude Code: Install and manage plugins](https://code.claude.com/docs/en/plugins/install)
- Removing a marketplace uninstalls every plugin installed from it — [Claude Code: Install and manage plugins](https://code.claude.com/docs/en/plugins/install)
- `claude -p` cannot run `/plugin` (it replies "`/plugin isn't available in this environment.`"), but plugins already installed still load there. Cloud sessions load neither locally installed plugins nor plugins enabled in the repo's `.claude/settings.json` — [Claude Code: Install and manage plugins](https://code.claude.com/docs/en/plugins/install)
- For testing, `--plugin-dir <dir>` loads a plugin for one session (its ID ends in `@inline`) — [Claude Code: Plugin loading reference](https://code.claude.com/docs/en/plugins/loading)

**On disk and in settings**
- `~/.claude/plugins/known_marketplaces.json` (one per user), `installed_plugins.json` and `cache/` (plugin files, at `~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/`). Plugin IDs look like `<name>@<marketplace>`, `@inline`, `@skills-dir` or `@synced` — [Claude Code: Plugin loading reference](https://code.claude.com/docs/en/plugins/loading)
- Team sharing of a marketplace: `extraKnownMarketplaces` in `.claude/settings.json`, e.g. `{"extraKnownMarketplaces":{"acme-tools":{"source":{"source":"github","repo":"acme-corp/claude-plugins"}}}}`, plus `enabledPlugins: {"plugin@marketplace": true}`. These repository entries are honored "only after you accept the workspace trust dialog" — [Claude Code: Settings reference](https://code.claude.com/docs/en/settings-reference)
- Claude Code "doesn't scan a project's `.claude/plugins/` directory". To share through a repo, use `enabledPlugins` in `.claude/settings.json` or put a plugin folder under `.claude/skills/` — [Claude Code: Plugin loading reference](https://code.claude.com/docs/en/plugins/loading)

**marketplace.json and plugin structure**
- `.claude-plugin/marketplace.json` requires `name`, `owner` and a `plugins` array. Each entry needs `name` and `source`. A source is a relative path from the marketplace root (no `..`), `{ "source": "github", "repo": "..." }`, `{ "source": "git-subdir", "url": "...", "path": "..." }`, `url`, `archive` (zip over HTTPS, can be `sha256`-pinned), `npm` or `command`. Keep the entry name identical to the `name` in the plugin's `plugin.json`. Validate with `claude plugin validate ./my-marketplace` — [Claude Code: Create a marketplace](https://code.claude.com/docs/en/plugins/create-marketplace)
- Plugin layout: `.claude-plugin/plugin.json` (required) plus optional `.mcp.json`, `commands/`, `agents/`, `skills/` and `README.md`. Marketplace `name` slugs are immutable; use `displayName` to relabel, or a top-level `renames` map to migrate installs — [anthropics/claude-plugins-official README](https://github.com/anthropics/claude-plugins-official)
- A plugin can also carry hooks (`hooks/hooks.json`), monitors, mods, MCP/LSP servers and a `bin/` directory that gets added to the Bash tool's `PATH` — [Claude Code: Plugin security and trust](https://code.claude.com/docs/en/plugins/security)
- **Outdated URL flag:** the old page `code.claude.com/docs/en/plugin-marketplaces` now serves "Create a marketplace". The plugin docs moved under `/docs/en/plugins/*` (overview, install, anthropic-marketplaces, security, create-marketplace, marketplace-reference, loading, cli-reference, org) — [Claude Code docs index](https://code.claude.com/docs/llms.txt)

### Inferences
- When another researcher recommends "plugin X", the install line is `/plugin install X@claude-plugins-official` if X is in the official catalog. Otherwise it is `/plugin marketplace add <owner>/<repo>` followed by `/plugin install X@<name field from that repo's marketplace.json>`. The name after `@` is the marketplace's `name`, which often differs from the repo name.
- To give a design or frontend team a consistent toolset, commit `extraKnownMarketplaces` + `enabledPlugins` in `.claude/settings.json`. Teammates still need to trust the folder and run the install once.

### Gaps
- The full current list of the 315 official entries changes often. The docs deliberately don't list it, so downstream researchers should verify each plugin name against `marketplace.json` or `/plugin` Discover at install time.

## 3. Adding MCP servers in Claude Code (transports, scopes, .mcp.json, /mcp, env vars, context cost and tool search)

### Takeaway
Use `claude mcp add --transport http <name> <url>` for remote servers and `claude mcp add [options] <name> -- <command> [args...]` for local stdio servers. Choose `--scope local` (the default, private, stored in `~/.claude.json`), `project` (written to `.mcp.json`, shared through git, approved per server) or `user` (all your projects). Authenticate OAuth servers with `/mcp` or `claude mcp login <name>`. SSE is deprecated. Tool search is on by default, so MCP tool definitions are deferred until Claude needs them, which keeps the per-server context cost low. Large tool outputs and always-loaded servers still cost context.

### Cited Findings
- HTTP is "the recommended option for connecting to remote MCP servers": `claude mcp add --transport http notion https://mcp.notion.com/mcp`. Add a header with `--header "Authorization: Bearer your-token"`. In JSON, `type` also accepts `streamable-http`. A JSON entry with `url` but no `type` is an error — [Claude Code: MCP](https://code.claude.com/docs/en/mcp)
- "The SSE (Server-Sent Events) transport is deprecated." From v2.1.265, `--transport http` falls back to SSE automatically. Explicit form: `claude mcp add --transport sse asana https://mcp.asana.com/sse` — [Claude Code: MCP](https://code.claude.com/docs/en/mcp)
- stdio: `claude mcp add --env AIRTABLE_API_KEY=YOUR_KEY --transport stdio airtable -- npx -y airtable-mcp-server`. Everything after `--` goes to the server untouched. Put another option between `--env` and the server name, otherwise the name is parsed as another env pair. The server's environment gets `CLAUDE_PROJECT_DIR` — [Claude Code: MCP](https://code.claude.com/docs/en/mcp)
- WebSocket: JSON only, e.g. `claude mcp add-json events-server '{"type":"ws","url":"wss://...","headers":{...}}'`. There is no `--transport ws` and no OAuth — [Claude Code: MCP](https://code.claude.com/docs/en/mcp)
- JSON form: `claude mcp add-json <name> '<json>'`, e.g. `claude mcp add-json local-weather '{"type":"stdio","command":"/path/to/weather-cli","args":["--api-key","abc123"],"env":{"CACHE_DIR":"/tmp"}}'`. Claude Code can also import servers from Claude Desktop — [Claude Code: MCP](https://code.claude.com/docs/en/mcp)
- Management: `claude mcp list`, `claude mcp get <name>`, `claude mcp remove <name>` (which also deletes stored OAuth tokens), and `/mcp` in a session for status, auth and enable/disable toggles. A toggle is stored per project in `~/.claude.json` as `disabledMcpServers` — [Claude Code: MCP](https://code.claude.com/docs/en/mcp)
- Scopes: local is the default (current project only, stored in `~/.claude.json` under `projects.<path>.mcpServers`); project goes to `.mcp.json` at the repo root, shared through git; user goes to `~/.claude.json` and applies to all projects. Precedence: local > project > user > plugin-provided > claude.ai connectors. The whole entry comes from the winning source, with no field merging — [Claude Code: MCP](https://code.claude.com/docs/en/mcp)
- Interactive sessions prompt for approval before using `.mcp.json` servers (reset with `claude mcp reset-project-choices`). **But** `claude -p`, Agent SDK and cloud sessions "load project-scoped servers without asking". To block one, use `disabledMcpjsonServers`, `--strict-mcp-config` or `--setting-sources` — [Claude Code: MCP](https://code.claude.com/docs/en/mcp)
- `.mcp.json` supports `${VAR}` and `${VAR:-default}` expansion in `command`, `args`, `env`, `url` and `headers`, so secrets can stay out of git — [Claude Code: MCP](https://code.claude.com/docs/en/mcp)
- OAuth: add the server, then run `/mcp` and log in through the browser, or run `claude mcp login <name>` from the shell. `-p` runs can't do OAuth, so authenticate interactively first. Use "Clear authentication" in `/mcp` to revoke — [Claude Code: MCP](https://code.claude.com/docs/en/mcp)
- Tool search: "Tool search is enabled by default: MCP tools are deferred and discovered on demand. Only tool names and server instructions load at session start ... Claude Code doesn't impose a fixed per-server tool cap; the practical limit is your context window budget." Control it with `ENABLE_TOOL_SEARCH` (`true`, `false`, `auto` = defer once definitions exceed 10% of context, or `auto:N`). It is disabled automatically when `ANTHROPIC_BASE_URL` points to a non-first-party proxy. Per-server `"alwaysLoad": true` exempts a server from deferral but makes startup wait for it — [Claude Code: MCP](https://code.claude.com/docs/en/mcp)
- Output limits: a warning above 10,000 tokens per MCP tool output. The default max is 25,000 tokens (`MAX_MCP_OUTPUT_TOKENS`). Over-limit text results are saved to a file under `~/.claude/projects/.../tool-results`. HTTP responses over 16 MiB fail — [Claude Code: MCP](https://code.claude.com/docs/en/mcp)
- MCP prompts appear as commands `/servername:promptname (MCP)` or `/mcp__servername__promptname` — [Claude Code: MCP](https://code.claude.com/docs/en/mcp)
- The [Anthropic Directory](https://claude.ai/directory) lists reviewed remote connectors that can be added with `claude mcp add`. The official `mcp-server-dev` plugin (`/plugin install mcp-server-dev@claude-plugins-official`, then `/mcp-server-dev:build-mcp-server`) scaffolds new servers — [Claude Code: MCP](https://code.claude.com/docs/en/mcp)
- Official docs say "CLI tools are the most context-efficient way to interact with external services" (e.g. `gh`) — [Claude Code: Best practices](https://code.claude.com/docs/en/best-practices)
- Visual feedback MCPs: Playwright MCP's README gives `claude mcp add playwright npx @playwright/mcp@latest` — [microsoft/playwright-mcp](https://github.com/microsoft/playwright-mcp). Chrome DevTools MCP's README config is `"command": "npx", "args": ["-y", "chrome-devtools-mcp@latest"]` — [ChromeDevTools/chrome-devtools-mcp](https://github.com/ChromeDevTools/chrome-devtools-mcp). Both also exist as plugins in the official marketplace (`playwright`, `chrome-devtools-mcp`) — [claude-plugins-official marketplace.json](https://github.com/anthropics/claude-plugins-official/blob/main/.claude-plugin/marketplace.json)
- Chrome DevTools MCP privacy defaults: Google usage statistics are on by default (opt out with `--no-usage-statistics` or `CHROME_DEVTOOLS_MCP_NO_USAGE_STATISTICS`). Performance tools may send trace URLs to the CrUX API (`--no-performance-crux` disables this). The server "exposes content of the browser instance to the MCP clients" — [ChromeDevTools/chrome-devtools-mcp](https://github.com/ChromeDevTools/chrome-devtools-mcp)
- There is also a built-in alternative, Claude in Chrome: `claude --chrome`. It needs the Chrome extension v1.0.36+, a direct Anthropic plan and `/login` (not an API key). It shares your browser's logged-in state, can save screenshots to disk and record GIFs, and is not supported in WSL — [Claude Code: Chrome](https://code.claude.com/docs/en/chrome)

### Inferences
- The `--` separator form is the documented Claude Code convention. A safer form of the Playwright command is `claude mcp add --transport stdio playwright -- npx @playwright/mcp@latest`; the README's form without `--` works only because that command has no flags of its own. Add `--scope project` to commit it to `.mcp.json` for a team, or `--scope user` for all projects.
- Tool search lowers the cost of having many MCP servers, so "keep tool count low" now matters mostly for servers marked `alwaysLoad`, for very large tool outputs (screenshots and DOM dumps can be big), for proxied or gateway setups where tool search is off, and for the attack surface. Pick one browser MCP (Playwright, Chrome DevTools or Claude in Chrome), not all three.
- Pinning versions (`@playwright/mcp@<version>` instead of `@latest`) reduces the "rug-pull" supply-chain risk described in section 6, at the cost of manual updates.

### Gaps
- No official per-tool token figure for deferred MCP tools was found. `/context` and `/doctor` report actual costs per session.

## 4. Cross-ecosystem installers and directories (npx skills / skills.sh, SkillsMP, claude-plugins.dev, awesome lists): trustworthiness and cross-agent compatibility

### Takeaway
The SKILL.md format works across agents (Claude Code, Codex, Gemini CLI, Cursor, Copilot and others). The main difference is the folder each agent reads: Claude Code reads `.claude/skills/` and `~/.claude/skills/`, while most others read `.agents/skills/`. Vercel's `npx skills add <owner/repo>` CLI (skills.sh) installs into the right folder for each agent. Community directories (skills.sh, SkillsMP, claude-plugins.dev) are crawlers or indexes, not vetted stores; the malware findings in section 6 included skills.sh. Anthropic's own repos and the official marketplace are the most trustworthy sources, and awesome lists are discovery aids only.

### Cited Findings
**Vercel `skills` CLI (skills.sh)**
- "The CLI for the open agent skills ecosystem". It supports "OpenCode, Claude Code, Codex, Cursor, and 75 more". Install with `npx skills add vercel-labs/agent-skills`. Sources can be GitHub shorthand, a full URL, a `/tree/main/skills/<name>` path, GitLab, Azure Repos, any git URL or a local path — [vercel-labs/skills](https://github.com/vercel-labs/skills)
- Flags: `-g/--global` (user dir instead of project), `-a/--agent <agents>` (e.g. `claude-code`, `codex`), `-s/--skill <names>` (`'*'` for all), `-l/--list`, `--copy` (instead of the default symlink), `-y`, `--all`. Example: `npx skills add vercel-labs/agent-skills --skill frontend-design -g -a claude-code -y`. Other commands: `npx skills list|find|remove|update|init` and `npx skills use <src> | claude` (use a skill without installing) — [vercel-labs/skills](https://github.com/vercel-labs/skills)
- Install paths: Claude Code → project `.claude/skills/`, global `~/.claude/skills/`. Codex, Cline, Zed, Warp and others → `.agents/skills/` / `~/.agents/skills/`. Cursor → `.agents/skills/` / `~/.cursor/skills/`. Gemini CLI → `.agents/skills/` / `~/.gemini/skills/`. - Feature compatibility table: "Basic skills" work in every listed agent. `allowed-tools` works in most (not Kiro CLI or Zencoder). `context: fork` works only in Claude Code. Hooks work in Claude Code, Cline and Kiro CLI — [vercel-labs/skills](https://github.com/vercel-labs/skills)
- The CLI collects anonymous telemetry, which can be disabled with `DISABLE_TELEMETRY` or `DO_NOT_TRACK` — [vercel-labs/skills](https://github.com/vercel-labs/skills)
- The CLI also discovers skills declared in `.claude-plugin/marketplace.json` / `plugin.json`, "for compatibility with the Claude Code plugin marketplace ecosystem" — [vercel-labs/skills](https://github.com/vercel-labs/skills)
- The anthropics/skills README shows a skills.sh badge (`skills.sh/anthropics/skills`), so Anthropic's skill repo is listed there too — [anthropics/skills](https://github.com/anthropics/skills)

The `.agents/skills` location comes from a third-party article, and an older doc used `~/.codex/skills` — [OpenAI Codex: Agent Skills](https://developers.openai.com/codex/skills); [Daniel Vaughan: Codex CLI skills ecosystem](https://codex.danielvaughan.com/2026/03/27/codex-cli-skills-ecosystem/)

### Inferences
- Rough trust ranking for sourcing: (1) the official marketplace `claude-plugins-official`, especially Anthropic-maintained `/plugins` and vendors' own first-party plugins (e.g. Microsoft Playwright, ChromeDevTools, Figma), plus `anthropics/skills`; (2) the community marketplace `claude-community`, whose entries are pinned to commit SHAs; (3) well-known vendor repos added via `/plugin marketplace add <vendor>/<repo>` or `npx skills add <vendor>/<repo>`; (4) awesome lists, used only to discover the source repo, which you then audit; (5) crawler indexes (SkillsMP, claude-plugins.dev, skills.sh search), which are unvetted.

- Installing via `/plugin` has advantages over `npx skills add`: namespaced commands, the "Will install" and context-cost preview, update tracking, and the `claude plugin details` inventory. `npx skills add` is better for skill-only repos shared across several agents.

## 5. Best practices for effective use (triggering descriptions, explicit invocation, lean CLAUDE.md, visual feedback loops, subagents, prompting)

### Takeaway
Write descriptions in the third person that state what the skill does and when to use it, with the key use case first. Invoke a skill explicitly with `/name` when it doesn't trigger on its own. Keep SKILL.md under 500 lines and CLAUDE.md under about 200 lines, and move the rest into references, rules or skills. Always give Claude a check it can run; for visual work that means screenshots compared with the target design. Delegate heavy exploration or review to subagents, and use `/doctor`, `/skill-doctor`, `/context` and `claude plugin details` to prune unused extensions that cost context.

### Cited Findings
**Descriptions and triggering**
- "Always write in third person. The description is injected into the system prompt". Include both what the skill does and when to use it, with specific key terms. Example: `description: Extract text and tables from PDF files, fill forms, merge documents. Use when working with PDF files or when the user mentions PDFs, forms, or document extraction.` Avoid "Helps with documents" — [Claude Platform: Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Naming: gerund form recommended (`processing-pdfs`), noun phrases acceptable. Avoid vague names (`helper`, `utils`) and reserved words — [Claude Platform: Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Claude Code advice: "Put the key use case first", because of the 1,536-char listing cap and because descriptions get dropped when there are many skills. Use `when_to_use` for trigger phrases — [Claude Code: Skills](https://code.claude.com/docs/en/skills)
- Troubleshooting a skill that doesn't trigger: (1) add keywords users would naturally say; (2) check that it appears in "What skills are available?"; (3) rephrase the request; (4) invoke `/skill-name` directly; (5) check for refused names. Malformed YAML loads the body with empty metadata, so auto-matching fails; diagnose with `--debug` or `claude plugin validate ~/.claude/skills` (v2.1.233+) — [Claude Code: Skills](https://code.claude.com/docs/en/skills)
- If a skill triggers too often, make the description more specific or set `disable-model-invocation: true` — [Claude Code: Skills](https://code.claude.com/docs/en/skills)
- Explicit invocation: `/deploy staging` at the start of a message runs the skill directly. Writing `/deploy` mid-sentence only grants Claude permission to run it — [Claude Code: Skills](https://code.claude.com/docs/en/skills)
- The anthropics/skills README says you can trigger a plugin skill by mentioning it, e.g. "Use the PDF skill to extract the form fields from ..." — [anthropics/skills](https://github.com/anthropics/skills)
- When Claude stops following a skill: move must-hold rules into hooks (including the skill's own `hooks` frontmatter); word guidance so it applies to the whole task ("Run the tests after every edit"); re-invoke after compaction and put the most important instructions at the top — [Claude Code: Skills](https://code.claude.com/docs/en/skills)
- Measure whether a skill helps: compare runs with and without it in fresh sessions, using `skillOverrides: {"name":"off"}` for personal and project skills or `claude plugin eval` for plugin skills. The `skill-creator` plugin automates evals — [Claude Code: Skills](https://code.claude.com/docs/en/skills)

**Structure**
- "Keep SKILL.md body under 500 lines", "Keep references one level deep from SKILL.md", add a table of contents to long reference files, avoid time-sensitive info, use forward slashes in paths, list required packages, and create at least three evaluations tested on Haiku, Sonnet and Opus — [Claude Platform: Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Reference MCP tools in skills with fully qualified names (`ServerName:tool_name`) to avoid "tool not found" errors — [Claude Platform: Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Prefer utility scripts over generated code ("Solve, don't defer"), and use feedback loops and verifiable intermediate outputs for quality-critical tasks — [Claude Platform: Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)

**CLAUDE.md and context hygiene**
- "target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence." Move part-specific rules into `.claude/rules/` with `paths` frontmatter — [Claude Code: Memory](https://code.claude.com/docs/en/memory)
- "Bloated CLAUDE.md files cause Claude to ignore your actual instructions!" For each line, ask "Would removing this cause Claude to make mistakes?" — [Claude Code: Best practices](https://code.claude.com/docs/en/best-practices)
- Every listed skill costs context on every turn. `/skill-doctor` (v2.1.252+) reports each skill's cost and usage and flags never-used ones. `/doctor` estimates the skill-listing cost and offers to migrate always-loaded guidance into skills. `/doctor prompt-audit` (v2.1.283+) audits instructions for conflicts. `skillOverrides` (states `on`/`name-only`/`user-invocable-only`/`off`, edited via the `/skills` menu) trims skills you don't want to edit. Plugin skills are managed through `/plugin` instead — [Claude Code: Skills](https://code.claude.com/docs/en/skills)
- The `/plugin` **Installed** tab shows a "Not used recently" group, and `claude plugin details <name>` shows the "Always-on" tokens a plugin adds — [Claude Code: Install and manage plugins](https://code.claude.com/docs/en/plugins/install)

**Visual feedback loop and verification**
- "Give Claude a check it can run: tests, a build, a screenshot to compare." Example prompt: "[paste screenshot] implement this design. take a screenshot of the result and compare it to the original. list differences and fix them". "Always provide verification (tests, scripts, screenshots). If you can't verify it, don't ship it." — [Claude Code: Best practices](https://code.claude.com/docs/en/best-practices)
- The bundled `/run` ("Launch and drive your app"), `/verify` (confirm a change without falling back to tests) and `/run-skill-generator` (records a launch recipe as `.claude/skills/run-<name>/`) handle browser-driven projects. A project skill named `verify` is run before each commit (v2.1.286+) — [Claude Code: Skills](https://code.claude.com/docs/en/skills)
- Claude in Chrome can do "Design verification: build a UI from a Figma mock, then open it in the browser to verify it matches", read console errors and DOM, and record GIFs — [Claude Code: Chrome](https://code.claude.com/docs/en/chrome)
- Platform best practices list "Use visual analysis" as a pattern for skills with executable code (e.g. converting a form to images for layout analysis) — [Claude Platform: Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)

**Subagents and prompting**
- "Delegate research with 'use subagents to investigate X'". Subagents run in separate context windows and report summaries. For an adversarial review, "have a subagent review the diff in a fresh context". `/batch <instruction>` fans out across 5–30 subagents in worktrees — [Claude Code: Best practices](https://code.claude.com/docs/en/best-practices)
- Failure patterns: the kitchen-sink session (fix: `/clear` between tasks); correcting over and over (after two failed corrections, `/clear` and rewrite the prompt); the over-specified CLAUDE.md; infinite exploration — [Claude Code: Best practices](https://code.claude.com/docs/en/best-practices)
- Ask Claude to learn unknown CLIs: "Use 'foo-cli-tool --help' to learn about foo tool, then use it to solve A, B, C." — [Claude Code: Best practices](https://code.claude.com/docs/en/best-practices)

### Inferences
- For SVG, video and 3D, "visual feedback loop" generally means a script or skill step that renders output to PNG frames (e.g. headless browser screenshot, video frame extraction, 3D viewport capture) that Claude can then view. A screenshot-capable browser MCP or Claude in Chrome serves web-based outputs. This is an extrapolation of the official "screenshot to compare" guidance; the specific tools come from other researchers.
- Put renderer- or library-specific rules in a skill whose `paths` frontmatter targets the relevant files (e.g. `**/*.svg`, `src/remotion/**`), so it auto-loads only when those files are being worked on.

### Gaps
- No official Anthropic guidance specific to SVG, video or 3D workflows was found; those recommendations must come from the domain researchers.

## 6. Security: risks of third-party skills, plugins and MCP servers, how to vet them, permissions and sandboxing

### Takeaway
Treat skills, plugins and MCP servers like installing software. A plugin "can execute arbitrary code on your machine with your user privileges". Hooks, monitors, MCP and LSP servers run outside the sandbox and outside permission rules. Skills can inject instructions and grant themselves tools through `allowed-tools`, and MCP tool descriptions can carry hidden prompt injections ("tool poisoning", "line jumping", "rug pulls"). Audits of public skill registries in February 2026 found real malware. Before installing, review the source; use `claude plugin details`, `--plugin-dir`, `Read`/`Bash`/`mcp__*` deny rules, `/sandbox` and containers, and turn off auto-update for marketplaces you don't trust.

### Cited Findings
**What third-party components can do (official)**
- "A Claude Code plugin you install can execute arbitrary code on your machine with your user privileges." Hooks run shell commands, monitors run background commands, mods run JavaScript, stdio MCP servers run as local processes, `bin/` lands on `PATH`, and skills, commands and agents "enter Claude's context as instructions" — [Claude Code: Plugin security and trust](https://code.claude.com/docs/en/plugins/security)
- "Claude Code's permission rules and sandbox cover the tool calls Claude makes, not the code a plugin runs by itself ... Claude Code runs hooks, monitors, MCP servers, LSP servers, and the processes a mod starts outside the sandbox." — [Claude Code: Plugin security and trust](https://code.claude.com/docs/en/plugins/security)
- With auto-update on, "the files you reviewed can change on disk" — [Claude Code: Plugin security and trust](https://code.claude.com/docs/en/plugins/security)
- Skills: "Use Skills only from trusted sources ... a malicious Skill can direct Claude to invoke tools or execute code in ways that don't match the Skill's stated purpose". Audit SKILL.md, scripts, images and other resources; "Skills that fetch data from external URLs pose particular risk"; "Treat like installing software" — [Claude Platform: Agent Skills overview](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview); [Anthropic Engineering post](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)
- A skill's `allowed-tools` is not gated by workspace trust: "Claude Code applies a project skill's `allowed-tools` even in a `-p` run in a folder you've never trusted ... review the `allowed-tools` of skills checked into a repository before you run Claude Code there." Organizations can neutralize it with `allowManagedPermissionRulesOnly` (v2.1.282+) — [Claude Code: Skills](https://code.claude.com/docs/en/skills)
- Before trust: in a `claude -p` run in an untrusted repo, hooks, the `env` block, `apiKeyHelper` and skill hooks/`allowed-tools` are "Used", and `.mcp.json` servers are "Connected without asking". Mitigations: `--setting-sources user`, `--bare`, `--settings '{"disableAllHooks": true}'`, `disabledMcpjsonServers` — [Claude Code: Permissions](https://code.claude.com/docs/en/permissions)
- MCP: "Verify you trust each server before connecting it. Servers that fetch external content can expose you to prompt injection risk." Anthropic reviews Directory connectors against listing criteria "but does not security-audit or manage any MCP server" — [Claude Code: MCP](https://code.claude.com/docs/en/mcp); [Claude Code: Security](https://code.claude.com/docs/en/security)

**Vetting workflow (official)**
- Run `claude plugin marketplace list` to check sources. Read the `/plugin` details pane (**Will install**). Read the plugin's `hooks/hooks.json`, `.mcp.json` and every file in `bin/`. Clone the repo and run `claude --plugin-dir <dir> plugin details <name>` to get a "Component inventory" without starting a session. After install, inspect `~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/` — [Claude Code: Plugin security and trust](https://code.claude.com/docs/en/plugins/security)
- Removal: `claude plugin uninstall <plugin> --scope <scope>`. The cache stays for 14 days (delete it by hand if you need to). Remove the whole marketplace if you don't trust its owner — [Claude Code: Plugin security and trust](https://code.claude.com/docs/en/plugins/security)
- Built-in guards: official and community marketplace names are accepted only from `github.com/anthropics/`, otherwise the marketplace is refused as "registered from an untrusted source". The `claude-community` catalog pins nearly every entry to a commit SHA, and archive sources can be `sha256`-pinned — [Claude Code: Plugin security and trust](https://code.claude.com/docs/en/plugins/security)
- Every plugin shows the trust warning: "Anthropic does not control what MCP servers, files, or other software are included in plugins and cannot verify that they will work as intended or that they won't change." — [Claude Code: Plugin security and trust](https://code.claude.com/docs/en/plugins/security)
- Snyk Agent Scan (repo `snyk/agent-scan`; the `invariantlabs-ai/mcp-scan` raw README returns the same content) "Discover[s] and scan[s] agent components on your machine for prompt injections and vulnerabilities (including agents, MCP servers, skills)". Run `uvx snyk-agent-scan@latest ~/.claude/skills` or `uvx snyk-agent-scan@latest <path/to/SKILL.md>`. It needs `SNYK_TOKEN`. **Warning:** "Scanning MCP configurations can execute commands", because it starts stdio servers to read their tools — [snyk/agent-scan](https://github.com/snyk/agent-scan)

**Permissions and sandboxing**
- Rules are "evaluated in order: deny, then ask, then allow". A deny at any scope beats an allow at any scope. Example: `{"permissions":{"allow":["Bash(npm run *)","Bash(git commit *)"],"deny":["Bash(git push *)"]}}`. Block secrets with `Read(./.env)` or `Read(./secrets/**)` — [Claude Code: Permissions](https://code.claude.com/docs/en/permissions)
- MCP rule syntax: `mcp__<server>__*` (all tools of a server), `mcp__<server>__<tool>` (one tool), `"mcp__*"` in deny (all MCP tools). Plugin servers use `mcp__plugin_<plugin>_<server>__*`. An unanchored allow glob like `"mcp__*"` is ignored with a warning — [Claude Code: Permissions](https://code.claude.com/docs/en/permissions)
- Skill rules: deny `Skill` to disable all skills, or use `Skill(name)` / `Skill(name *)` to allow or deny specific ones — [Claude Code: Skills](https://code.claude.com/docs/en/skills)
- A blocking hook (exit code 2) "stops the tool call before permission rules are evaluated" — [Claude Code: Permissions](https://code.claude.com/docs/en/permissions)
- The sandbox is off by default. Turn it on with `/sandbox` or `sandbox.enabled`. It uses Seatbelt on macOS and `bubblewrap` + `socat` on Linux/WSL2, and is built on `@anthropic-ai/sandbox-runtime`. For one boundary around everything (including plugin processes), run Claude Code itself in a container, VM or the sandbox runtime — [Claude Code: Sandboxing](https://code.claude.com/docs/en/sandboxing)
- Security doc best practices: use VMs for scripts and tool calls that touch external web services, avoid piping untrusted content to Claude, audit with `/permissions`, and use a dev container or sandbox runtime for sensitive code. `curl`/`wget` are not auto-approved — [Claude Code: Security](https://code.claude.com/docs/en/security)
- Organizations can allowlist or blocklist marketplace sources, force-enable plugins, disable `--plugin-dir`, restrict hooks to managed ones and stop claude.ai-synced plugins (`syncClaudeAiPlugins`) — [Claude Code: Plugin security and trust](https://code.claude.com/docs/en/plugins/security)

**Independent security research**
- Snyk "ToxicSkills" (Feb 2026), as reported by a search-engine summary of the Snyk post: it scanned 3,984 skills from ClawHub and skills.sh (as of Feb 5, 2026). 13.4% (534) had at least one critical issue (malware distribution, prompt injection, exposed secrets), and 36.82% (1,467) had at least one flaw of any severity. Secondary sources cite 76 confirmed malicious payloads. **Conflict:** an AgentGuard summary calls the 1,467 figure "malicious payloads", which contradicts Snyk's any-severity framing — [Snyk: ToxicSkills](https://snyk.io/blog/toxicskills-malicious-ai-agent-skills-clawhub); [AgentGuard AGS-2026-0006](https://agentguard.gopluslabs.io/advisor/AGS-2026-0006)
- Koi Security "ClawHavoc" (Feb 2026): 341 malicious skills out of 2,857 on ClawHub (OpenClaw's registry), 335 of them from one campaign. They used fake "Prerequisites" (download a password-protected ZIP or run an obfuscated shell script) to install the Atomic Stealer (AMOS) macOS infostealer. A later update reported 824 malicious skills as the registry grew past 10,700. Antiy CERT counts at least 1,184 historically — [Koi: ClawHavoc](https://koi.ai/blog/clawhavoc-341-malicious-clawedbot-skills-found-by-the-bot-they-were-targeting); [The Hacker News](https://thehackernews.com/2026/02/researchers-find-341-malicious-clawhub.html); [Antiy CERT](https://www.antiy.net/p/clawhavoc-analysis-of-large-scale-poisoning-campaign-targeting-the-openclaw-skill-market-for-ai-agents/)
- Invariant Labs (April 2025) described "tool poisoning": hidden instructions in an MCP tool's description, e.g. a harmless "add" tool told to read `~/.ssh` keys. It also described "rug pulls", where servers change tool definitions after approval via `notifications/tools/list_changed`. Its scanner mcp-scan has become Snyk Agent Scan (above). The MCPTox benchmark reports an average 36.5% attack success rate across 20 models (secondary source) — [CSA research note on MCP tool poisoning](https://labs.cloudsecurityalliance.org/research/csa-research-note-mcp-tool-poisoning-auto-execution-20260701/); [Kayssel: MCP Security](https://kayssel.substack.com/p/mcp-security-poisoning-the-tools)
- Trail of Bits (Apr 21, 2025), "line jumping": a malicious MCP server injects instructions through `tools/list` descriptions that take effect when the server connects, before any tool is called. Clients including Claude Desktop followed such instructions. Trail of Bits released `mcp-context-protector` (beta) as a defensive wrapper — [Trail of Bits: Jumping the line](https://blog.trailofbits.com/2025/04/21/jumping-the-line-how-mcp-servers-can-attack-you-before-you-ever-use-them/)

### Inferences
- Practical vetting checklist for any recommended skill, plugin or MCP:
  1. Prefer the official marketplace or the vendor's own repo.
  2. Read SKILL.md plus every script for network calls, `curl | bash`, "prerequisite" downloads, obfuscated code, or out-of-scope file access (`~/.ssh`, `.env`, browser profiles).
  3. Check `allowed-tools`, `hooks` and `.mcp.json`/`bin/` in plugins.
  4. Run `claude --plugin-dir <clone> plugin details <name>` before installing.
  5. Optionally scan with `uvx snyk-agent-scan@latest` (in a throwaway environment, since it runs servers).
  6. Pin versions and refs (`owner/repo#tag`, `pkg@x.y.z`) and keep auto-update off for third-party marketplaces.
  7. Add deny rules (`Read(./.env)`, `Bash(curl *)` if appropriate) and enable `/sandbox`. Use a dev container for untrusted repos or media pipelines that download assets.
- Browser MCPs (Playwright, Chrome DevTools, Claude in Chrome) read live web content, the main route for prompt injection. Run them against local dev servers or a separate browser profile, not your logged-in daily profile, unless authenticated access is needed.
- The ClawHub/ClawHavoc incidents were on OpenClaw's registry rather than Claude's marketplaces. The skill format is the same, though, and skills.sh was included in Snyk's corpus, so the risk carries over to any SKILL.md you `npx skills add` from an unknown author.
